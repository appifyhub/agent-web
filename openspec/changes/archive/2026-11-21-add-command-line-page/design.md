# Design

## Context

See `proposal.md` for motivation and `specs/command-line-page/spec.md` for the behavioral contract. Cross-repo decisions (auth model, endpoint table, CLI behavior) come from the approved abot CLI context: the CLI is authorized by attaching to the user that owns a connect key, the key rotates after a successful CLI connect, and "revoke all" is a single backend operation that kills every CLI token for the user at once.

Current web code this change builds on:

- **Routing.** `src/App.tsx` registers every settings page as a flat `<Route path="/:lang_iso_code/user/:user_id/<slug>">`; the closest sibling is `linked-profiles` → `LinkedProfilesPage`.
- **Page identity.** `src/lib/settings-pages.ts` owns the `SettingsPage` union and `getSettingsPageTitle()`. That union flows into `BaseSettingsPage`, `Header`, `AuthRequiredPage`, and `AnalyticsPageId`; two analytics records (`PAGE_PATHS`, `PAGE_TITLES` in `src/lib/analytics.ts`) are typed `Record<AnalyticsPageId, string>`, so adding a page id fails the TypeScript build until both have entries.
- **Navigation.** `src/hooks/useNavigation.ts` exposes one `navigateToX(userId, langIsoCode)` per page (preserving search params except `token`). `src/components/Header.tsx` builds the sidebar/mobile drawer from `navigationSections` (`personal`, `agent`, `resources`, `people`), maps destinations through `navigateToUserPage()`, and derives `currentSectionLabel` from the current page.
- **Session and shell.** `src/hooks/usePageSession.ts` provides the token, error state and loading flag; `src/pages/BaseSettingsPage.tsx` (note: under `pages/`, not `components/`) wraps `Header`, the page title, action bar, `topBanner`, error presentation (`ErrorMessage`), onboarding gate and canonical page-view analytics for any `SettingsPage`.
- **Connect key.** `src/services/connect-key-service.ts` already exposes `getConnectKey` and `regenerateConnectKey` (both `Authorization: Bearer <web JWT>`, errors via `parseApiError`). `LinkedProfilesPage.tsx` shows the key, its formatter `formatDisplayKey` (private), a clipboard `handleCopy` (private, with an `execCommand` fallback and `toast(t("copied"))`) and the copy-row markup (mono span + icon button + `Tooltip`).
- **Networking and errors.** `src/services/networking.ts#request` adds a 10 s timeout; `src/lib/api-error.ts` has `ApiError`, `parseApiError`, `getErrorTranslationKey`; `PageError.fromApiError()` in `src/lib/utils.ts` carries `apiErrorCode` and `httpStatus` so `BaseSettingsPage` classifies 401/4001–4003 as authentication failures for analytics.
- **i18n.** Eleven catalogs in `src/assets/i18n/` (`ar, de, en, es, fr, hi, it, ru, sr, tr, zh`; same list as `INTERFACE_LANGUAGES`); `src/lib/translation-keys.ts` is generated by `bun run lint` (`lint:i18n` → `scripts/generate-translation-keys.ts`, which also validates JSON, duplicates, key parity, placeholder parity and non-English key ordering; `scripts/check-translation-usage.ts` fails on unused keys). User-facing product naming is `{botName}` = `import.meta.env.VITE_APP_NAME_SHORT`.
- **Analytics.** `src/lib/analytics.ts` offers typed `trackFeatureAction({featureId, action, result?, optionId?, sourceArea?, apiErrorCode?, httpStatus?})`; `optionId` must match a stable-id pattern (`^[a-z0-9][a-z0-9_-]{0,63}$`) or it is dropped; `getErrorDetails(err)` extracts safe error metadata. The conventions come from the archived change `openspec/changes/archive/2026-08-27-add-web-app-analytics/` (typed allowlist, no JWTs/keys/ids, canonical page location and title, `sourceArea` = page id).
- **Testing reality.** The repository has no automated test framework or `test` script (the archived analytics design records this as deliberate). Verification is `bun run lint` (i18n generation/validation, ESLint, Stylelint, Tailwind spacing check), `bun run rebuild` (`tsc -b` + Vite build), and manual browser verification, as in earlier changes. This change does not introduce a framework.

## Goals / Non-Goals

**Goals:**

- A single, reviewable page that takes a user from "what is this" through install and connect to revoke, using only existing shell, services, and visual patterns.
- Zero new runtime dependencies and zero new authentication paths in the web app.
- Install and connect commands that are correct to paste verbatim and easy to correct centrally if distribution names change.
- Complete translations in all eleven locales from day one.

**Non-Goals:**

- Any backend, CLI, or Helm work (owned by the backend and CLI changes).
- Listing individual CLI devices or sessions, showing token expiry, or a per-device revoke: the product has no device table and "revoke all" is deliberately opaque.
- Chat/notify features of the CLI, or any web UI for sending notifications.
- A new test framework, version bump (`bun run bump` is a maintainer step done in separate commits in this repo), or changes to CI workflows.
- Handling or storing CLI tokens in the web app, in any form.

## Decisions

### Route, page id, and naming

Page id `command_line` (snake_case like `linked_profiles`), route `/:lang_iso_code/user/:user_id/command-line` (kebab-case like `linked-profiles`), navigation helper `navigateToCommandLine(userId, langIsoCode)`, translation namespace `command_line`, component `CommandLinePage` in `src/pages/CommandLinePage.tsx`. The title key is `command_line.page_title` ("Command Line"), wired through `getSettingsPageTitle()`. Analytics path `/app/command-line` and title `${APP_NAME} | Command Line` are added to `PAGE_PATHS` / `PAGE_TITLES`. The shared page-view tracking in `BaseSettingsPage` needs no change.

Alternative considered: nesting under `/access` or `/linked-profiles` as a tab. Rejected: the context requires its own route registered next to the other settings pages, and the topics (API keys, profile merging) differ.

### Navigation placement: "Agent" section, between Intelligence and Help

The CLI is another way of reaching the agent, not an account-resource (`resources` = usage/purchases/API access) and not about other people (`people` = sponsorships/linked profiles). Add the entry to the `agent` section after `intelligence` and before `help`, with the lucide `Terminal` icon, visible under the same condition as the other user pages (`canNavigateToUserPages`). Extend the `navigateToUserPage()` destination union and map, and add `command_line` to the `agent` branch of `currentSectionLabel` so the shell header shows "Agent" on the page.

Alternative: `resources` after Access. Rejected: Access is billing-adjacent (API keys) and the CLI is a client of the agent.

### Page composition (modeled on `LinkedProfilesPage`)

`CommandLinePage` calls `usePageSession()` and renders `BaseSettingsPage` with `page="command_line"`, `cardTitle`, `showActionButton={false}` (like `HelpPage`: the page has no single save-style action), `contentVariant="flow"`, `isContentLoading={isLoadingState}`, `externalError={error}` and `onExternalErrorDismiss`. Content is four `SettingsSection` cards, in order:

1. **About**: what the CLI is (two short paragraphs, `{botName}` interpolated): runs on the user's computer, connects with the connect key, sends notifications to the user's chats; plain statement that it never gets the user's API keys. (Text must not promise features beyond v1: auth + notifications.)
2. **Install**: the shared `CardSelector` used on Intelligence, with macOS / Linux / Windows and Apple / Bird / Grid2X2 icons. `showSelectedCheckmark={false}` preserves platform icons when selected. Every OS presents its package manager first, including an official Homebrew or Scoop installer link, then a separate manual-download alternative linking GitHub Releases. Manual instructions cover the correct archive type (`.tar.gz` on macOS/Linux, `.zip` on Windows), arm64/amd64 selection, checksum verification, extraction and PATH placement of the configured binary. macOS includes its minimum version and a copyable, branded quarantine-removal command only after verification; Windows includes the documented SmartScreen warning. Linux additionally offers `.deb`/`.rpm` commands after its download instructions. All external links use the underlined link style from Onboarding. The final shared step verifies installation with the configured CLI name and `--version`.
3. **Connect**: translated intro, the key row (amber mono key, copy and regenerate icon buttons exactly like the existing key row), the `abot connect <KEY>` `CopyableCommand`, and a note that the key is secret, changes after each successful connect, and can be regenerated.
4. **Revoke**: a red-bordered section with explanation text and the destructive "Revoke all CLI access" button that opens the confirmation.

The key fetch mirrors the existing `useEffect` in `LinkedProfilesPage` (guarded on `accessToken`, `user_id`, and `error`; `setIsLoadingState`; blocker `PageError.fromApiError(err, true)` / `PageError.blocker("errors.fetch_failed")`). Sections 1–2 and 4 render regardless of the key; if the fetch fails the blocker modal makes the page unusable, consistent with the sibling page.

### Install content lives in one data module

`src/lib/command-line.ts` exports typed constants only (no JSX, no translated text): the releases URL, an `INSTALL_COMMANDS` record per OS id (`macos | linux | windows`) with the ordered commands and a stable analytics option id each, `detectCommandLineOs(userAgent)`, `buildConnectCommand(formattedKey)` returning `abot connect <key>`, and `VERIFY_COMMAND = "abot --version"`. Commands are code, never translated:

| OS | Commands (option id) |
|---|---|
| macOS | `brew install appifyhub/tap/abot` (`homebrew`) |
| Linux | `brew install appifyhub/tap/abot` (`homebrew`); `sudo apt install ./abot_*.deb` (`apt`); `sudo dnf install ./abot-*.rpm` (`dnf`) |
| Windows | `scoop bucket add appifyhub https://github.com/appifyhub/scoop-bucket` (`scoop_bucket`); `scoop install abot` (`scoop`) |

The default names match the CLI distribution: Homebrew tap `appifyhub/tap`, Scoop bucket `appifyhub/scoop-bucket`, and Linux packages `abot_<ver>_<arch>.deb` / `abot-<ver>-1.<arch>.rpm`. Package commands assume the corresponding download is in the current directory. Archives are available for every OS; the README documents unsigned downloads, checksum verification, macOS 13 minimum, Gatekeeper quarantine handling and Windows SmartScreen prompts. Security-prompt guidance belongs to the manual path, not the package-manager instructions.

macOS and Linux installs also provide the short alias formed by prefixing the configured CLI name with `@`. The translated description interpolates `{cliAlias}` and `{cliName}` as amber, monospaced `<code dir="ltr">` elements. `CardSelector` accepts optional React-node descriptions to preserve translation word order without HTML injection. Windows instructions use the configured command name without discussing the unavailable alias or rendering an empty paragraph.

`detectCommandLineOs()` inspects `navigator.userAgent` with the same style of regex the repo already uses for mobile detection (`Windows` → windows, `Mac OS X|Macintosh` → macos, `Linux|X11` → linux; Android/iOS/unknown → `macos`). The initial tab is detected once; it is the user's selection afterwards. Android UAs contain `Linux`, so mobile patterns are checked first and fall back to the default.

`VITE_APP_CLI_NAME` configures the CLI command name at build time, alongside `VITE_APP_NAME_SHORT`; its default is `abot`. It is documented in `.env.example`, set in the local `.env`, and passed from repository variables in the release workflow. `src/lib/command-line.ts` derives the alias, Homebrew/Scoop package names, Linux package globs, verify command and connect command from this one value. Repository URLs and the AppifyHub tap/bucket identities are unchanged. Browser verification with the override `orbit` confirmed all commands, clipboard output and rich translated names use the configured name; all eleven locales rendered resolved placeholders.

### Shared extractions instead of a second convention

Three small private pieces of `LinkedProfilesPage` are needed here; copy-pasting them would create a second convention, so they are extracted and the existing page migrated in the same change:

- `src/lib/connect-key.ts`: `formatConnectKey(key)` (the body of `formatDisplayKey`). `LinkedProfilesPage` replaces its local function with the import (same behavior).
- `src/lib/clipboard.ts`: `copyText(text): Promise<boolean>`; the Clipboard API with the existing hidden-textarea `execCommand("copy")` fallback, returning `false` instead of throwing. It never toasts. Both pages use it through `CopyableCommand`; the Linked Profiles copy-failure text and disabling behavior remain unchanged. `CopyValue.tsx` is left alone (different, simpler contract; not part of this change).
- `src/components/CopyableCommand.tsx`: shared mono text + copy button + tooltip row used by both pages, including all three Linked Profiles rows and the Command Line key row. It supports `textRef`, `textClassName`, `beforeCopy` and trailing `children` so the existing share/regenerate controls retain their order and behavior. `copyTooltipText` and `copyErrorText` allow page-specific translations. `onCopy` runs before the copy attempt (Linked Profiles analytics); `onCopied` runs only after success (Command Line analytics). Copying uses `copyText`, success toasts `t("copied")`, and failure invokes `onCopyFailed`. Text stays selectable, horizontally scrollable and LTR. Browser verification covered both pages' copied text, regeneration, mobile share payloads with a simulated native API, cancellation, and independent copy/share failure disabling; lint and rebuild passed.

### Revoke: service, confirmation, and flow

- **Service.** New `src/services/cli-access-service.ts` with `revokeCliTokens({apiBaseUrl, user_id, rawToken}): Promise<{status: string}>`: `DELETE ${apiBaseUrl}/user/${user_id}/cli/devices`, headers identical to `connect-key-service.ts` (`Content-Type: application/json`, `Authorization: Bearer ${rawToken}`), no body, via `request()`, throwing `await parseApiError(response)` when `!response.ok`. A new file (not `connect-key-service.ts`) because it is the CLI-access concern, matching the repo's one-service-per-domain layout. No cache layer (a mutation with no readable state).
- **Confirmation.** New generic `src/components/ConfirmDialog.tsx` built on `ui/dialog.tsx` (`Dialog`, `DialogContent`, `DialogHeader`, `DialogTitle`, `DialogDescription`, `DialogFooter`): props `open`, `onOpenChange`, `title`, `description`, `actionButtonText`, `onActionClicked`, `actionDisabled?`, `cancelButtonText?` (default `t("command_line.cancel")`), `isActionPending?`, `destructive?` (destructive `Button` variant). It ignores close requests (overlay click, Escape, X) while `isActionPending`. Alternative: reusing `WarningBanner`'s `destructiveLabel` as `AccessSettingsPage` does for "Remove All". Rejected: that action is local and reversible (Save is still needed); revoking is immediate and irreversible, so an explicit modal is required by the context ("button with confirmation").
- **Flow.** Button → open dialog (`trackFeatureAction({featureId:"cli_access", action:"open"})`) → cancel (`action:"cancel"`) or confirm → `isRevoking` true → `revokeCliTokens`. On success: close dialog, `toast.success(t("command_line.revoke_success"))`, `trackFeatureAction({featureId:"cli_access", action:"revoke", result:"success"})`. On failure: close dialog (so the non-modal `ErrorMessage` is reachable), `setError(err instanceof ApiError ? PageError.fromApiError(err) : PageError.simple("command_line.generic_error"))`, track `result:"failure"` with `...getErrorDetails(err)`. `finally`: `isRevoking` false. `isRevoking` (local state) is used instead of `setIsLoadingState`, because the latter replaces the whole page with a skeleton.
- **Auth.** The request uses `accessToken.raw` from `usePageSession` (the web JWT). A 401 yields `PageError` with `httpStatus: 401`, which `BaseSettingsPage` already reports as `api_authentication_failed`; the page does not add its own redirect or `handleTokenExpired` call, matching all sibling pages.
- **Success presentation.** A toast is used for success only (consistent with `regenerate_success` and `saved`); failures never use toast, per `AGENTS.md`.

### Errors and API error codes

All service errors go through `parseApiError` and `PageError.fromApiError` (loading failures as blockers via the second argument `true`, action failures non-blocking). Unmapped codes keep degrading to `errors.unknown` with the server message.

**Ten CLI-access codes must be mapped:** eight present in the current backend, plus 3010 and 6004 for compatibility with the current CLI by explicit user decision. The backend's archived change is `../agent-backend/openspec/changes/archive/2026-11-15-add-cli-access/design.md` (D16 error table); current backend API docs and implemented definitions take precedence for its actual contract. `../agent-cli/internal/api/codes.go` names the additional codes `CodeDeliveryRefused` and `CodeProviderRateLimited`; do not restore their obsolete names `chat_unreachable` / `notification_rate_limited`. These codes need translations even though the page normally cannot trigger them. Add cases to `getErrorTranslationKey()` in numeric position and append catalog keys in the table's order in every locale:

| Code | Contract name / source | HTTP | Key | English text |
|---|---|---|---|---|
| 1043 | `INVALID_CLI_TTL` | 400 | `error_codes.invalid_cli_ttl` | Invalid command-line access lifetime |
| 1044 | `CLI_TTL_TOO_LONG` | 400 | `error_codes.cli_ttl_too_long` | Command-line access lifetime is too long |
| 1045 | `INVALID_CLI_DEVICE` | 422 | `error_codes.invalid_cli_device` | Invalid command-line device information |
| 1046 | `INVALID_NOTIFICATION_MESSAGE` | 422 | `error_codes.invalid_notification_message` | Invalid notification message |
| 2015 | `CONNECT_KEY_NOT_FOUND` | 404 | `error_codes.connect_key_not_found` | Connect key not found or already used |
| 3010 | `CodeDeliveryRefused` (CLI compatibility) | 403 | `error_codes.delivery_refused` | The platform refused to deliver the message |
| 4004 | `INVALID_CLI_TOKEN` | 401 | `error_codes.invalid_cli_token` | Invalid command-line access token |
| 4005 | `CLI_ACCESS_REVOKED` | 401 | `error_codes.cli_access_revoked` | Command-line access was revoked |
| 5018 | `NOTIFICATION_DELIVERY_FAILED` | 502 | `error_codes.notification_delivery_failed` | Failed to deliver the notification |
| 6004 | `CodeProviderRateLimited` (CLI compatibility) | 429 | `error_codes.provider_rate_limited` | The provider's request limit was reached. Try again later |

Wording follows the existing `error_codes` entries (short, no product name; "agent" is not needed here). In the catalogs they are appended after the last existing `error_codes` entry in the same order, which keeps non-English ordering identical to `en.json`. `scripts/check-translation-usage.ts` treats `error_codes.*` keys as used when they appear in `getErrorTranslationKey()`, so lint enforces mapping and catalog completeness together.

**HTTP 400.** The backend adds a `BadRequestError` (HTTP 400) for the two TTL codes. `parseApiError()` already reads `error_code` and `message` from any JSON error body regardless of status, and `PageError.fromApiError()` carries both code and status without status-specific branches, so 400 needs no code change; the task list verifies this by inspection and by a stubbed 400 response rather than assuming it.

**Authentication classification.** The web's existing classification (`BaseSettingsPage`: HTTP 401, or codes 4001–4003) is left as is. 4004 and 4005 are only returned to CLI tokens on CLI routes, never to the web JWT on web routes (web 401s keep the `{detail}` body without an error code), and any such response is a 401 anyway, which the existing classifier already treats as an authentication failure.

### Translations

All strings live under `command_line.*` in `en.json` first (source of truth for key order), then are mirrored with real translations into the other ten catalogs in identical order and with identical placeholders (`{botName}`, `{connectKey}` only where needed). Planned keys:

`page_title`, `card_title`, `copy_command`, `copy_failed`, `cancel`, `generic_error`; `about_title`, `about_description` (`{botName}`), `about_privacy`; `install_title`, `install_intro`, `os_macos`, `os_linux`, `os_windows`, `install_homebrew`, `install_apt`, `install_dnf`, `install_scoop_bucket`, `install_scoop`, `install_package_note`, `install_verify`, `releases_link`; `connect_title`, `connect_intro`, `key_label`, `command_label`, `key_rotation_note`, `key_secret_note`, `copy_key`, `regenerate_key`, `regenerate_success`; `revoke_title`, `revoke_description`, `revoke_button`, `revoke_dialog_title`, `revoke_dialog_description`, `revoke_confirm`, `revoke_in_progress`, `revoke_success`; plus `install_alias_note` (macOS/Linux `@abot` alias). The ten `error_codes.*` keys from the table above are added in the same catalogs, including `delivery_refused` and `provider_rate_limited` with real translations in all eleven locales. The unused Windows alias note is removed from every catalog.

`install_manager_note` uses `{packageManager}` to insert the official Homebrew or Scoop installer link before the corresponding package-manager command. `install_alias_note` uses `{cliAlias}` and `{cliName}` rather than literal command names. These placeholders are mirrored in every locale.

The manual alternative uses `install_manual_intro`, `install_manual_steps` (with `{archiveType}` and `{cliName}`), `install_manual_macos_note` and `install_manual_windows_note` in all eleven locales. It appears after Homebrew/Scoop and before Linux package commands; no manual download is required for a package-manager installation.

The navigation entry label reuses `command_line.page_title` (no duplicate key), consistent with `linked_profiles.page_title`. The final key set is whatever the implementation actually uses; `bun run lint` enforces both "no unused" and "no missing in any locale". Wording rules: "the agent"/`{botName}`, never "bot"; "CLI" is spelled out as "command-line" on first use in prose; `abot` is a product command and stays Latin in all locales.

### Analytics

Extend `src/lib/analytics.ts` types only: `AnalyticsFeatureId` += `"cli_connect_key" | "cli_install" | "cli_access"`; `AnalyticsFeatureAction` += `"revoke"`; page maps get `command_line`. Events (all `sourceArea: "command_line"`):

| Interaction | featureId | action | optionId | result |
|---|---|---|---|---|

| copy connect command | `cli_connect_key` | `copy` | `command` | |
| regenerate key | `cli_connect_key` | `regenerate` | | success/failure (+error details) |
| copy install command | `cli_install` | `copy` | install option id (`homebrew`, `apt`, `dnf`, `scoop_bucket`, `scoop`) | |

Documentation: the archived analytics change added no in-repo registry file (`git ls-files` shows no analytics doc), so there is no registry to update; the allowlist is the TypeScript types.

### Page layout details

Reuse existing Tailwind patterns from `LinkedProfilesPage` verbatim for the key row; use `font-mono`, `overflow-x-auto`, `whitespace-nowrap` for commands so long commands scroll rather than wrap or truncate; `lint:tw` enforces the spacing convention. No new CSS files. Icons from `lucide-react` (`Terminal`, `Copy`, `RefreshCw`, `ExternalLink`, `ShieldAlert` or `Trash2` for revoke).

The shared non-blocking `ErrorMessage` wrapper needs `lg:bottom-auto` alongside `lg:top-30`; otherwise its mobile `bottom-5` anchor remains active on desktop and stretches an invisible click target over the page. The one-class correction was verified by normal retry clicks while errors were visible; the desktop wrapper now measures only the alert's content height. Blocking-dialog behavior remains unchanged.

## Risks / Trade-offs

- [Distribution names drift if the CLI release pipeline renames its tap, bucket, or packages] → The names are confirmed against the CLI change today and live in one module, `src/lib/command-line.ts`, with a consistency check task.
- [Backend endpoint not deployed when the page ships] → The page degrades to the standard non-blocking error; the proposal states the dependency; manual verification of revoke needs the backend change or a local stub.
- [The displayed connect key goes stale after a successful CLI connect (the key rotates server-side)] → The page tells the user the key changes after each use and offers regenerate; reloading the page fetches the current key.
- [Connect key visible on screen and copied to clipboard] → Same exposure as `LinkedProfilesPage`; explicit secrecy note; never sent to analytics or logged (the page must not `console.info` the key or token, unlike token-decoded logging already in `usePageSession`).
- [Revoke is irreversible and instant] → Modal confirmation, single-submission guard, explanation that CLIs must be reconnected with a new key.
- [Shared extraction regresses Linked Profiles] → Extraction is mechanical, behavior-preserving, and covered by an explicit manual check of the Linked Profiles copy flow plus lint/build.
- [Translation quality for ten non-English locales] → Short, plain sentences; commands stay untranslated; mechanical checks by `bun run lint`; native-speaker review is out of scope as with earlier changes.
- [No automated tests exist in this repo] → Verification is lint, rebuild, and a scripted manual matrix in the tasks; no framework is introduced.

## Migration Plan

No data or configuration migration. Deploy with the normal release flow. Rollback is reverting the change; the backend endpoint is additive and unaffected. Ship order across repos: backend endpoint first (or concurrently); the web page is safe to ship earlier because the revoke failure path is handled.
